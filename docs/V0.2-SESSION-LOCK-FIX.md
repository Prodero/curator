# Curator 0.2.0 — Session writer exclusion

Date: 2026-10-21. Base candidate: `64eaf50e85b3c13c23146f5856aa99a713d2ee4a`. Scope: prove and repair the cross-process record/close race, retain exact acknowledgment semantics, verify a new scoped commit and its CI. No schema migration, memory backfill, installed-runtime change, merge or publication.

## Failure and evidence

The [original full matrix](https://github.com/Prodero/curator/actions/runs/39616627486) passed three of four jobs. macOS / Node 22.23.3 failed `M3: cross-process record/record and record/close preserve every acknowledged ID`: 11 successful observation acknowledgments, 10 IDs in the final synthetic session. The test waits for all child processes, and workers acknowledge only after the awaited session mutation. This establishes a fixture durability violation; it does not establish loss of real user knowledge.

A separate deterministic baseline reproduction establishes the stale-owner interleaving with IPC and filesystem barriers, without retries or timing-based luck:

1. Writer A owns the lock and is inside its critical section.
2. Contender B reads A's PID under `lock-recovery`, then pauses before returning that read.
3. A releases the lock and exits.
4. Successor C acquires the same lock pathname and enters its critical section.
5. B resumes, probes A's now-dead PID and removes the lock at that pathname. B acquires it and enters while C is still inside.

The baseline assertion fails because B and C overlap. The original protocol serialized only stale reapers; acquisition, owner publication, cleanup and normal release did not share that exclusion. Consequently a stale-owner decision could remove a successor's live lock. The exact scheduling of the earlier CI failure was not traced; the deterministic reproduction proves this concrete mechanism independently.

## Chosen boundaries and acceptance

Use the existing per-worktree recovery guard to serialize all lock topology transitions, including creation/owner publication, stale-owner probing/removal, creation-failure cleanup and release. Do not hold that guard throughout the canonical operation. Preserve numeric PID ownership, private permissions, path checks and operation-scoped writer capabilities.

Unknown/missing owners and an interrupted recovery guard remain bounded fail-closed/manual-inspection states. Do not reclaim a live PID, infer death from age or move the same ABA race into automatic guard recovery. Project schema 8, knowledge schema 3 and journal/checkpoint order remain unchanged.

Acceptance must cover deterministic successor protection and mutual exclusion, every acknowledged record/record and record/close ID, dead-owner recovery, late-record rejection, bounded unknown-owner/guard behavior, creation/release errors, and existing private-path/permission and migration readiness contracts. Existing M3 assertions are retained. Stress complements deterministic regressions and must not serve as retry-until-green masking.

Independent review, targeted/stress checks, the full clean local release gate, strict UI types and installed-artifact acceptance precede scoped delivery. The final commit and exact-SHA fast/full CI results are recorded in the task receipt and GitHub artifacts; earlier successful runs are not a substitute. User config and original audits remain byte-preserved outside the commit, and the private backup ancestry stays local.

## Pre-commit verification

The same deterministic regression failed against the baseline build with `stale reaper entered an occupied critical section` and passes against the repair. Independent review found no blocking protocol or oracle defects. The final targeted batch passed **86/86** checks, including 13 new concurrency/error regressions, existing M3, private path/permission and intelligence tests. A fixed **20-round** stress plan passed **80/80** checks (three unchanged M3 tests and the deterministic reaper regression per round), without retries after failure. The new barrier-started record/record and record/close test exercises 72 child-process attempts per run and compares every successful acknowledgment with final persisted IDs.

The added error regressions verify ordinary owner-publication cleanup, replacement preservation, operation-error cleanup, release with an expired acquisition deadline, and release timeout without a successful acknowledgment. Production server build and diff whitespace checks pass. Full clean local verification and remote CI must still run on the committed follow-up SHA; their outcome is not inferred from these targeted results.
