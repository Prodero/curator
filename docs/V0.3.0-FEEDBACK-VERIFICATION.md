# 0.3.0 candidate: Close receipt and explicit memory actions

Local checkpoint on `work/v0.3.0`, based on `51da46f`. Package identity remains 0.2.1; this is unreleased 0.3.0 development. No commit, push, release, external deployment or real project-memory operation was performed for these checks.

## Close visibility

A fresh isolated client launched with the actual saved Codex command reproduced a synchronized, persisted Close whose human text was only `**Saved**` followed by `1 observation recorded`. This proves a presentation regression; it does not establish whether Close ran in the user's particular conversation, whose session ID was not provided. The former relay instruction also allowed a confirmation to remain in commentary before the final answer.

The shared receipt now requires an actual `session.status === closed`. Confirmed synchronized states explicitly say `Session closed`; replay says `Session already closed`; deferred synchronization says `Saving deferred`. Zero observations remain visible. Missing proof of closure says `Session status unavailable`, never a fabricated success. Counts describe recorded observations, not newly created knowledge records. Existing optional diagnostics stay visible without undoing a successfully persisted Close.

The host-agent instruction places the one-line Close receipt in the final answer, even for quiet or zero-observation cases. A visible App need not be duplicated. This is a delivery instruction to the current host agent, not a guarantee that every host/model renders or follows it.

Exact English text examples:

- `**Session closed** · Saved 1 observation.`
- `**Session closed** · No observations recorded.`
- `**Session already closed** · 1 observation previously recorded.`
- `**Session closed** · Saving deferred.`

## Open and historical revisions

Normal Open/status details previously consulted the saved curation recommendation. Loading an unsupported or malformed historical revision could consequently make ordinary project opening display a revision error. Open now reads the normal project/memory overview without loading curation history. Genuine storage, save and migration errors retain their existing paths.

Explicit Curate Memory uses a fresh current-knowledge preview. A sealed `historyPolicy: fresh-current` records this isolation; it is validated and hash-bound, and is not an Apply capability. It starts without inherited choices, approvals or old pause state. Unavailable historical reviews remain byte-preserved and count as pinned retention entries. Exact access to an invalid saved review still fails closed. Unknown history policies, tampered revisions, changed sources, invalid dependencies and stale selections do not become valid by choosing a fresh preview.

The graphical flow requires deliberate group selection, simulation and the existing exact reviewed Apply. Rendering never creates choices or performs Apply. Text offers the full current/proposed preview and simulation; protected curation Apply retains its existing graphical approval boundary. Bounded Local reconciliation during an ordinary task remains a separate current-session agent workflow.

The user's actual persisted historical review was not read or modified. The failure class was reproduced with an incompatible revision in a disposable project. Already-running server modules or already-open App cards may remain cached until the user reconnects the existing MCP connection.

## Explicit Local to Versioned

Both Open interfaces expose Curate Memory and selected Local-to-Versioned sharing. The visual action starts with unchecked Local IDs; preview sends only the chosen IDs. Text record detail offers the same exact-ID preview. The complete existing promotion proposal must be reviewed and explicitly approved before writing Versioned files. Cancel, browsing and preview do not write shared memory. No commit or push is implicit. Existing migration/access/source/revision checks remain intact.

The old unsolicited moderation queues, routine counters and housekeeping questions remain absent. Keeping explicit user-initiated management corrects the earlier overly broad navigation removal.
