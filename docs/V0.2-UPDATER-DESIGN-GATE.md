# Curator v0.2.0 — terminal-only npm update contract

Date: 2026-10-18. Implementation baseline: `951416a40e0a8243b2852e7e3155cf34c10926bb`, branch `work/v0.2.0`. Status: **IMPLEMENTED AND LOCALLY VERIFIED — terminal-only updater; real-host/browser/remote release gates remain separate**.

## Accepted direction and superseded proposal

The user chose a simpler separation: Codex/Claude show an available-version indicator; its action explains `prodero update` in a terminal. Only that CLI installs the package. The CLI asks the user to finish active work and close Codex/Claude before explicit continuation. Afterward the user restarts the host; Open/Prepare separately offer any required project migration.

This replaces the earlier U01 proposal for chat-initiated self-update, an external persistent admission launcher, all-consumer proof, detached runner, independent host executor and exact offline dependency closure. Those were stronger proposed guarantees, not requirements of this accepted scope. Their underlying npm/process observations remain valid. No daemon, universal process registry, automatic host shutdown, hot activation or atomic rollback is introduced. Earlier research remains in Library version history; this document defines the active contract.

The user authorized implementation, isolated npm/artifact tests in the existing Docker lab and local thematic commits. Working Mac npm installation, real host registrations/dev selection, Playwright/Chromium installation, push/merge and release publication remain excluded. Preserve the user's `.prodero/config.json` diff and audit documents. The implementation plan is intentionally updated for this scope.

## User journey and compatibility

1. In graphical or text mode, available-version information has the same meaning. Its action shows a readable instruction to run `prodero update` in a terminal; it does not execute npm or ask the agent to do so. Existing text/graphical layout and pending text-design/naming decisions are preserved.
2. Retain the existing `prodero_update` tool ID for older hosts/conversations, with an instruction-only title/description and read-only behavior. Even explicitly injected development release sources must not stage code, rebuild a checkout, refresh project integration or schedule project maintenance through this MCP tool.
3. In the terminal, `prodero update` resolves the exact current public stable version for preview. `prodero update VERSION` selects an exact stable version. The command checks installation, package identity, engines and target artifact before asking to continue. The preview identifies versions and the unchanged destination prefix.
4. The prompt says to finish active work and close Codex/Claude, explains temporary unavailability and restart, and requires explicit continuation. Cancellation/EOF has no install effect. Non-TTY execution refuses safely unless both exact VERSION and explicit `--yes` are present; that flag acknowledges the same shutdown requirement. No process search or killing occurs.
5. CLI waits for npm and verifies the installed version/public command afterward. A real npm failure, signal, timeout or failed verification returns a nonzero result with repair guidance. Installation can leave partial changes; there is no automatic retry or rollback claim.
6. User restarts/reconnects the host. Package mode then loads the updated package. A saved dev selection still loads its existing checkout; updating the package does not rebuild, switch or update that checkout. Describe installed package and active dev identity separately.
7. Open/Prepare compare project/knowledge formats and offer the existing exact migration plan when needed. Package update never scans projects or invokes migration/Sync/knowledge writers. Review-required migrations retain their restrictions.

## Bounded installation contract

Support one demonstrated ordinary Unix npm-global layout for exactly `@prodero/curator`: current real package root under the checked prefix's `lib/node_modules`, matching public bin, writable same-user ownership and checked absolute Node/npm. Reject source checkouts, npm links, workspace/cache layouts, alternate managers, mismatched prefixes, ambiguous provenance and inadequate permissions with an actionable explanation. Never choose another installation from ambient PATH, relocate a prefix, invoke sudo or repair ownership automatically.

Bind current package, target exact version, expected name/bin, compatible Node engines, official public npm source and artifact integrity. Download/validate the target artifact before replacement; do not execute registry prose or arbitrary URLs/commands. Installation uses fixed argv, no shell, explicit prefix and a neutral temporary cwd. Control npm configuration/environment so inherited prefix/loader overrides cannot redirect or inject the operation. Recheck the chosen installation before mutation.

Use ordinary npm dependency resolution. The exact top-level artifact is verified; the entire transitive dependency tree is not promised to be frozen or available offline. No private cache/shrinkwrap platform is required. Scripts policy must match the prebuilt artifact: current package has build/prepack scripts rather than consumer install hooks; candidate and production artifact checks must demonstrate that disabled install scripts still yield working CLI/MCP. Required native/install hooks are unsupported initially, not silently ignored and reported successful.

Keep the synchronous terminal controller loaded before replacement. Post-install inspection uses already loaded builtins/fixed subprocesses and cannot depend on importing changed `dist` modules, project integration or host managers. npm and Node must remain outside the mutation footprint. No persistent launcher/public-entry ownership migration is necessary: npm normally owns/restores its own bin link.

## Accepted concurrency and recovery limits

Closing hosts is a user action, not a machine-verifiable statement about every possible consumer. Unknown direct launches or another package-manager operation can race with installation; the updater does not claim universal exclusion. Users must not run those concurrently. Existing MCP processes continue old code until restart and may fail if they lazily read replaced resources. A warning and explicit maintenance acknowledgement are the scope boundary; automatic global MCP discovery/shutdown is not required.

An active terminal owns this operation and waits. Loss of the terminal/process can leave an uncertain package state. Inspect the installed public CLI/version and use the package manager's repair path before rerunning blindly. Preserve unrelated project/preferences/host files, including private receipt provenance. Updating the package is distinct from repairing unrelated registrations after an intentionally changed install location.
