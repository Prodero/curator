# Prepare / Close text verification

Local candidate on `work/v0.3.0`. Package version remains 0.2.1, unreleased 0.3.0 development. No commit, push, release, installation, MCP configuration change or host restart occurred.

## What was verified and adjusted

The saved Codex MCP command, arguments and managed PATH were checked against the actual Codex TOML entry and native receipt, without printing credentials. That exact command was launched with a disposable HOME and project. Its runtime instruction path points into the candidate checkout. A before/after matrix exercised actual tool responses rather than only snapshots.

The existing default Prepare and Close were already ordinary Markdown without the Open logo, terminal frame or numeric menu. Close correctly distinguished observations from knowledge created. The approved Open golden remains byte-identical.

Three small presentation issues were addressed:

- Prepare omitted zero categories and described completely empty context only as “No matching project context.” It now reports all three actual delivered array lengths, including zero. The renderer consumes structured counts instead of parsing English summary strings. Stored totals, token metrics and earlier bootstrap/read-only snapshots are not substituted.
- Deferred Close repeated “Saving deferred” twice. It now emits one receipt plus one short recovery sentence.
- Technical Close notices still used a generic “Useful knowledge was saved automatically” sentence, even when a successful empty session created no knowledge. They now use the same confirmed-state receipt as compact text. This is a copy correction; session persistence and synchronization are unchanged.

The host relay instruction also explicitly forbids inventing a session ID or closing another session when no successful Prepare ID is known for the current task. A missing-ID/not-found error is not proof that the project has no other active sessions. Existing final-answer delivery, error, approval, access and reconciliation rules remain intact.

## Actual runtime examples

In a synthetic loaded fixture, Prepare returned exactly:

> **Context Ready**
>
> Loaded 1 project instruction · 1 knowledge record · 0 skills.
>
> Continuing the task.

The empty fixture returned the same layout with `Loaded 0 project instructions · 0 knowledge records · 0 skills.` In this fixture explicit read-only Context selected one skill, while Prepare selected zero; each response reported its own arrays rather than replacing the Prepare count with stored/read-only counts.

The positive Close returned:

> **Session closed** · Saved 2 observations.

Core reported two persisted observations but only one newly created knowledge record after deduplication. A retry returned `Session already closed · 2 observations previously recorded.` An empty Close said `Session closed · No observations recorded.` Deferred synchronization said `Session closed · Saving deferred.` followed once by `It will resume before the next work session.` No output claims that two knowledge records were saved.

Russian prose remains a host-agent translation under the existing relay contract; no new localization engine or unverified Russian snapshot is substituted for actual English runtime output.

## Native host delivery limit

Runtime text, model-visible relay instructions and the App-invisible fallback were verified through actual MCP responses. **The final visible message of a live Codex host/LLM was not independently verified.** This executor exposes no direct connected Prodero tools. The supported desktop request `codex_app.list_threads({limit:30})` did not return a result and its waiting cell was terminated. It was a read-only request; whether the backend completed that read is unknown. No thread was opened, resumed or changed, no alternative private session/log route was used, and no new model/provider/task was launched to bypass the limitation. An SDK client executes the protocol, not a chat host, so it cannot certify final visible delivery. The Mac shell and saved-command runtime remained available; this is not evidence that the Mac was offline.

The selected candidate source/build are updated. Reconnect the existing Curator MCP connection and request fresh lifecycle output to verify its rendering in Codex. No running Codex/MCP process or unrelated task was restarted or interrupted.
