# Zod 4 release follow-up — 2026-11-05

Status: unpublished Curator **0.3.0** candidate. The Zod advisory is corrected and owner-completed npm authentication/read-write package access are verified. Exact-commit release CI and native-host acceptance remain separate publication requirements. This work does not publish the package or deploy the website.

## Applicability and correction

[GHSA-mrhx-c7xc-m3w5](https://github.com/advisories/GHSA-mrhx-c7xc-m3w5) affects collection validation before an upper bound is enforced. The [upstream fix](https://github.com/colinhacks/zod/pull/6652) rejects oversized bounded arrays, sets and maps before traversing their elements.

A small reproduction through Curator's actual `distillSchema`, with 13 invalid candidates against a limit of 12, demonstrated the affected behavior without allocating a large input:

| Runtime | First element visited | Validation issues |
| --- | --- | --- |
| Zod 3.25.76 | Yes | 14 |
| Zod 4.6.7 | No | 1, `too_big` |

This establishes applicability of the vulnerable validation behavior. It is not a demonstrated remote attack against Curator. Curator uses local stdio, not an HTTP server; provider output also has existing byte limits. MCP inputs and structured data still deserve bounded validation before per-element error accumulation. Evidence: `/tmp/curator-zod4-advisory-reproduction.json`.

The root dependency is now **Zod 4.6.7**, using its actual v4 validators. No application or bundled-plugin import uses `zod/v3`. Production `npm audit --omit=dev` reports **zero advisories**. The obsolete direct `zod-to-json-schema` dependency was removed; SDK's own compatibility dependency remains transitive.

## Compatibility changes

- Explicit string keys replace the old one-argument `z.record` API.
- Sparse enum-key telemetry uses `z.partialRecord`, preserving old files that omit unused categories.
- Native `z.toJSONSchema` replaces the old converter for provider/reconciliation/transformation contracts and the bundled migration plugin. Draft-7, input/default semantics and inline shared schemas are selected explicitly.
- The first broad run exposed an empty JSON Schema in the plugin's old converter path. That path was corrected, and the plugin's 16 focused tests passed.
- Project schema **8**, knowledge schema **3**, persisted formats, approval/revision checks and tool identities remain unchanged. Main working dependencies and the running MCP were not replaced or restarted; builds and production installs use task-owned temporary copies/prefixes.

All 55 public MCP tool schemas compile with a JSON Schema validator. Native conversion changes schema representation: inlined references, disjoint discriminated-union alternatives, explicit UUID patterns/safe-integer bounds, and input schemas for objects that strip unknown fields. These are not advertised as byte-identical JSON Schemas. Strict persisted/proposal objects retain unknown-key rejection. Existing valid values/defaults are tested separately from new rejection of invalid UUIDs or unsafe integers.
