Branch: `work/v0.3.0`, based on `51da46f`. This is an unreleased candidate; package metadata remains 0.2.1. No commit, release, client configuration change, native host restart, or real project-memory mutation was performed for this audit.

## What was actually exercised

Text acceptance launches the command/arguments selected by the existing Codex integration after checking them against its ownership receipt. Each process receives a disposable HOME/state directory and synthetic project. Six live stdio test groups exercise the public text gateway, its rendered Markdown and exact action bindings. They do not certify the host LLM’s final message.

Visual acceptance compiles the production `src/ui/main.ts` and CSS. Only the host App transport is substituted: actual Chromium clicks call the same configured stdio runtime with the real MCP App capability. Successful responses, revisions, previews and Apply guards come from that runtime. Explicitly named transport failures are injected to check recovery. Chromium version: 156.0.8078.4. Ten browser groups produced 21 passed checks, zero failed checks and one explicitly not-run conditional check. Nine representative final screenshots were inspected as pixels and retained locally.

This is the repository’s production-App/browser acceptance pattern, not a claim that the Codex iframe/postMessage bridge or final chat response was exercised. No browser profile belonging to the user was opened. The sandbox browser launch was refused before any page opened; the standard approved escalation then launched a disposable browser profile. See the [Playwright screenshot documentation](https://playwright.dev/docs/screenshots) for the capture mechanism.

## Defects fixed in this audit

All production edits for this audit are in `src/ui/main.ts`; storage, authority and approval contracts are unchanged.

1. Knowledge detail/Back lost the selected page because the retained filters were not updated from the successful result. Adopt the returned options so page, filters and record identity stay aligned.
2. Initialize could show “Prodero initialized” after a failed tool response. Require a non-error payload and actual returned initialized status before changing the UI to success.
3. A successful Local → Versioned Apply followed by a list refresh failure could retain completed selections and obscure whether the write happened. Preserve the confirmed publication count, clear completed selections before the optional reload, and show the refresh error alongside the receipt.
4. Mark cached catalogue data explicitly after a failed read and disable selection/edit actions until a fresh catalogue succeeds. The cached count is not represented as current state.
5. An initial failed Knowledge/Curate read could resemble a successful empty result. Render unavailable/loading states, unknown counts as em dashes, visible errors and explicit retry instead.

Four fast regression tests cover page return, failed initialization, successful publication plus failed refresh, and initial catalogue failure. Optional `test/open-navigation.mcp.mjs` and `test/open-navigation.browser.mjs`, with `test/helpers/live-app-browser.mjs`, retain the live acceptance scenarios. No real project memory is read into the fixture pages.
